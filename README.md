# ZhaJinWenQianCake

**自主研发的本地人像修图项目**：人像精修引擎 + 桌面应用。
全部代码、模型选型与素材从零实现与整理，不含任何第三方商业产品的
代码、模型或素材。

- 全离线运行，照片不出本机
- Python (FastAPI) 引擎 + ONNX 推理 + WebView2 桌面窗口
- 调光调色 / 人像精修 / 抠图换背景 / 消除 / 批量 / RAW / 联机拍摄

**方式 A · 普通用户**：到 [Releases](https://github.com/wmc-ccb/ZhaJinWenQianCake/releases) 下载发行包，解压后**双击 `ZhaJinWenQianCake.exe`** 即可，无需安装任何东西。两个版本任选：

## 背景消除（纯色背景）

针对纯色背景（证件照/影棚）的四项专项处理：

| 项 | 解决的问题 | 判据 |
|---|---|---|
| 祛穿帮 | 背景露出墙/地面/灯架 | 背景内异色连通块，用周围背景色填 |
| 祛瑕疵 | 背景布污点/灰尘/小褶皱 | 高通响应超过背景自身噪声水平 |
| 光影均匀 | 打光一侧亮一侧暗 | 拟合低频曲面，归一化到中位数 |
| 祛色彩断层 | 8 位量化色带 | 低梯度区亚像素抖动打散台阶 |

**前提是准确的背景掩膜**——纯色背景下可以从颜色直接算出来，不依赖模型
识别「这是背景」，这是这几项能做好而通用 AI 换背景做不好的原因。

### 自动保护

`purity()` 先量背景有多纯（用**去趋势后的残差**，因为平滑光影渐变不算
不纯）。实测：纯背景 1.000、带渐变 0.908、复杂夜景 0.020。纯度低于 0.45
时自动跳过并如实报告原因——在复杂背景上重处理等于把背景糊掉。

### 换底色用色键，不用分割模型

纯色背景换底色走 `color_key_alpha()`（四角色键 + 连通域清理），实测与
真值 IoU **0.986**，纯背景区误差 **0.0004**、纯主体区误差 **0.0004**。

早期版本用 MODNet 抠图，合成测试里**身体区域 alpha 掉到 0，底色透到身上**
——模型假设画面是真人，对道具/静物/几何体不可靠。这种错误比「边缘不够
干净」严重得多，所以纯背景优先色键。

## 图库

- **三模块**：图库 / 精修 / 创意，共用同一个画布与会话，切模块不丢编辑
- **技术分组**：抖动 / 欠曝 / 过曝 / 重复照片 / AI 精选。阈值取**这一批
  自身的分位数**——夜景和日光的「正常」不是一个数，固定阈值会把整批夜景
  标成欠曝
- **性能**：NEF 内嵌 JPEG 预览提取（632ms→13ms）、`IMREAD_REDUCED_COLOR_8`
  解码、12 线程并发、缩略图 LRU 缓存。24 张 26 MP RAW：41.6s → 0.6s
- **根目录扫描**：后台线程 + 缓存，首次调用 0.01s 返回「扫描中」


## AI 祛路人（确定性管线）

主流修图软件的「AI 祛路人」是云端生成功能；本地替代走**确定性管线**：

```
双尺度人脸检测 → 主体重叠判定 → 头身比例掩膜(与主体相交剔除) → LaMa 填充
```

实测（_DSC7550.jpg，900px 工作副本）：

- 路人（60×71px 小脸）稳定检出，主体（120px）不误判
- 路人掩膜与主体占比 **0.000**；消除后主体 **maxΔ=0.000**
- LaMa 填充：路人区 meanΔ=0.158，远处背景 maxΔ=0.010

### 检测分辨率的关键实测

YuNet 的检出率对输入尺寸**不是单调的**：同一张 60px 路人脸，长边
900–1300px 稳定检出，**1400px 以上反而消失**（分数归一被稀释）。而
preview 通常是 1399px，正好卡在失效边界。所以 `find_passersby` 把长边
>900 的图先降到 900px 检测，框再映回原尺度——这一步把 API 从
`removed=0` 修成 `removed=1`。

### 为什么不用"生成式认路人"

`selfie_multiclass` 是**单主体**模型：它对背景里的第二个人输出"背景"。
用模型认路人这条路在现有模型下走不通，只能靠编。YuNet 的框位置确定，
配合 LaMa 的填充能力，效果与可控性都更好。


## 我的预设（推荐 / 我的）

预设列现在是双 tab（与主流修图软件的习惯一致）：**推荐**（内置 7 个）/ **我的**
（用户保存）。服务端存 JSON（`server/_user_presets.json`），随
`/api/presets` 一起返回，前端不分两套数据流。

规则：内置名不可覆盖（409）；同名需显式 `overwrite`；只保存管线认识的
参数（未知键拒绝）；空态有引导文案；保存后自动切到「我的」并出现卡片；
卡片悬停出删除钮。

### 修掉的竞态

保存后列表**永远少一张卡**，链路是：

```
保存成功 → PRESET_PARAMS 非空 → loadPresetParams() 早退返回旧表
        → 新预设不在表里 → 渲染出旧列表
```

修复两层：
1. `loadPresetParams(force)`——保存/删除后强制重拉参数表；
2. `renderPresetCol` 加**代际号**——它是 async（先 await 再写 DOM），
   "点 tab 的旧渲染"会在"保存后的新渲染"之后醒来，把列表覆盖成空态；
   写 DOM 前检查自己是否仍是最新的渲染，不是就丢弃。

### 附带修掉

`#sideBody` 有两条冲突定义（`display:flex` 被后面的 `overflow-y:auto`
覆盖），双列布局实际从未生效——预设列和参数列一直是竖排堆叠的。
删掉旧规则后三列（预设 128 / 参数 281 / 历史 150）精确落位。

## 图库信息面板（智能预览 + 元数据）

单击照片显示信息卡（双击才打开编辑，挑图流程不中断）：

- **元数据**：文件名 / 曝光四参数 / 机身 / 镜头 / 拍摄时间 / 作者 / 技术分组标签。

### 修复：EXIF 曝光字段读不到

Nikon 写相机把曝光字段放在 **Exif IFD（0x8769）**，主 IFD 只有机身/时间/
版权——之前只读主 IFD，ISO/光圈/快门全是 `None`。合并子 IFD 后完整读出
（实测 `_DSC7550.jpg`：ISO 100 · 43mm · f/2.8 · 1/200s · NIKON Z6_3 ·
TAMRON 28-75mm F/2.8）。

### 修复：facecrop 500

端点里 `import cv2 as _cv` 之后用了 `cv2.INTER_AREA`——名字不存在，
NameError 直接 500。本地进程内复现拿到真实 traceback 定位。

## 证件照（规格裁切 + 换底色）

证件照换背景的本地确定性实现：

| 规格 | 输出像素 |
|---|---|
| 一寸 25×35 | 295×413 |
| 二寸 35×49 | 413×579 |
| 小二寸 35×45 | 413×531 |
| 签证 35×45 | 350×450 |
| 护照 33×48 | 390×567 |

底色：白 / 蓝 / 红 / 灰。头部定位用人脸框锚定解剖比例，头顶空间不足时
**用估计背景色补边再裁**（补的区域马上被换掉，不可见），而不是缩小视野
——缩小会让头撑满画面（实测过）。

### 换底色为什么默认不做"保留打光"

`keep_lighting` 把新底色乘以原背景亮度来"保留打光"，但原背景有高对比
图案时（白色纹路墙纸、条纹背景），乘出来的就是**图案本身**——实测白色
纹路背景换白底后纹路全部留着。证件照要的是规范要求的纯净平色，所以默认
关闭。

### 修掉的两个 bug

1. **连通域清理从未执行**：`a[..., 0]` 在 2D 数组上是"取第一列"，
   `connectedComponentsWithStats` 收到 1D 抛错又被 `except: pass` 吞掉。
   39 个 <234px 的发顶噪点全留着。改成 `a.astype(np.uint8)` 后噪点清除。
2. **头部占比算反了**：`view_h = head_h/ratio` 里 head_h 用 1.55×脸高，
   实测脸框只占画面 0.36~0.42（规范下限 0.45），方向搞反。改用
   头顶=脸上缘-0.42×脸高、头高=1.72×脸高 重新推导，实测 0.36（脸框）
   对应头部 0.62，落在规范 0.60~0.70 内。

## 「宠物」为什么是空的

`selfie_multiclass` 只有 6 类且全是人像相关（背景/头发/身体皮肤/脸部
皮肤/衣物/配饰），没有宠物分割。主流修图软件的宠物类需要专门的动物模型；
没有模型就如实标注空缺，不拿人像模型硬套。


## 图库「闭眼」分组

主流修图软件图库的 AI 挑图分组里有「闭眼」。连拍几十张总有几张闭眼，逐张
看很费时间。

**判据设计**：标准 EAR（眼睛纵横比）需要每只眼的 6 个轮廓点，而 YuNet
只给 5 点（眼中心/鼻尖/两嘴角），没有眼皮轮廓。所以用两个可测量的替代量：

1. **眼椭圆内的暗像素占比**——睁眼瞳孔暴露，暗像素多；闭眼眼皮覆盖，
   明显减少
2. **眼区纵向梯度能量**——睁眼有上/下眼睑边缘，闭眼趋于平滑

两项都低于**本批次 20 分位**才判闭眼。阈值取批次分布而非固定常数：
妆效、光线、人种都会改变"正常眼睛"的绝对值，固定阈值会整批误判
（和抖动/欠曝同一个道理）。

实测：睁眼 `open=0.693` vs 闭眼 `0.325`；合成批次真值 `[2,5]` 精确挑出。


## 换天空（确定性，无生成模型）

换天空。管线：

1. **识别**：背景分割（selfie_multiclass 的 background 类）∩ 颜色似然
   （蓝天色相带 190-250° / 过曝低饱和灰）。只用颜色会在白衣服上误判，
   分割先排除人物/前景是关键。实测室内图 coverage 0.0002（不误判）。
2. **地平线约束**：逐行天空似然衰减到峰值 45% 的行以下清零——地面反光
   （玻璃幕墙、水面）不该被替换。
3. **新天空**：程序化生成。竖直渐变（gamma 1.6 让地平线更亮）+ 太阳
   光晕 + 分形值噪声云。6 预设：晴空/深邃蓝天/夕阳金橙/暮色紫/柔灰阴天/
   晨曦青粉。
4. **亮度匹配**：新天空按原天空上/下部的中位亮度缩放（gain 限幅
   0.55-1.8），合成不突兀。实测 gain=1.377。
5. **羽化合成**：蒙版开运算去碎斑 + 高斯羽化，树梢/天线不被硬边切断。

实测户外人像：天空占比 16%，人物区（画面下 40%）逐像素差 0.0000，
换天后上部蓝度 +0.201。

## AI 补草地（确定性 + LaMa）

AI 补草地。管线：

1. **草地似然**：绿色色相带 90-150°（中心 115°）+ 中低亮度。水泥地/
   木板路不在带内。
2. **穿帮判据**：草地环境的**膨胀区**（核=宽/6，大杂物的中心本身不是
   草色但仍在草地环境里——小核会让 26px 椭圆的中心漏掉，实测修过）内
   颜色离草地中位色 >0.16、又不是主体的连通块。
3. **修补**：LaMa 以周围草地为上下文填充（窗口机制只跑含 mask 的窗口）。
4. **如实说明**：画面绿色占比 <5% 时 applicable=false（室内/影棚图
   不适用），不硬猜。

实测：合成图 2 处穿帮（暗背包+白纸）全部识别并补全，补全区 G=0.487
（草地 G≈0.48）；中下部人物区逐像素差 0.0000（与换天空同一保护逻辑）。

## 去道具（灯架/柔光箱/三脚架，确定性 + LaMa）

用户要求的功能。管线：

1. **杆件**：暗色低饱和像素 → **纯竖直**闭运算（1×h/60，椭圆核哪怕宽
   3px 也会逐行桥接三脚架斜腿，两次实测踩坑）→ 连通域 → **列游程**判据
   （有一段 ≥18% 画高的连续竖直像素）。列游程是必须的：三脚架腿与杆在
   关节处**几何相连**，整个支架是一个连通块，bbox 判据必然失效。
2. **灯头**：杆顶窗口内 gray>0.80 的低饱和大块（0.55 太宽——普通墙面
   就满足，整个背景连成一块后灯头反而被过滤，实测）。
3. **三脚架腿**：杆 bbox 下半段、宽度按**杆宽** 9 倍的窗口内的暗色像素
   全收（按 bbox 宽算会把窗口拉到画面边、误伤旁边的人，实测）。
4. **主体保护** + **LaMa 补全**。

实测合成场景：杆/柔光箱/两条斜腿全部识别并补成背景色（偏差 <0.01），
人物区逐像素不动（0.0000）。

## 四季背景（春樱/夏空/秋叶/冬雪，确定性）

同类软件的季节按钮多用生成式；这里做确定性等价实现：

1. **分割保人物**：selfie_multiclass 的 subject 类，前景膨胀 3px 后软边
   （防发丝处被背景色包出描边）。
2. **程序化季节场景**：底色渐变 + 场景元素（樱花树影/云/树冠用分形噪声）
   + 方向性粒子（花瓣斜落 0.5rad、落叶 0.9rad、雪花近垂直）。粒子有
   景深感：远的小而淡（55%）、近的大而略糊。
3. **结构明暗保留**（keep_structure=0.25）：把原背景的相对亮度以低权重
   叠回场景色——墙面透视/地面阴影还在，只是换了季节色彩，不假。
4. OpenCV 5.0 的 ellipse 不收 np.float32 数组当颜色（实测报错），转
   Python 元组。

实测：四季节上部色调互异（0.59~0.89），人物掩膜内逐像素差
0.0004~0.0007（几乎不动），每季 0.3~2.1s。

## RAW（NEF）全流程 + RAW EXIF 写回（verify_raw_workflow.py）

Z6 III 拍 NEF，摄影师的主路径就是 RAW。冒烟：上传（2~3s）→ 调色

## 这是什么

2026 年 10 月，我用 REA 静态分析了一台机器上安装的商业修图软件，提取出它的
**功能清单与参数体系**（调色项、美肤项、美型项、工作流结构）。那份分析给了我一份
"需求规格"。

ZhaJinWenQianCake 就是照着这份规格、用公开的图像处理算法与公开模型重新实现的一套引擎：

- 覆盖同样的功能面：光影、存在感、白平衡、美肤、五官、美型、身形、细节、镜头、
  颗粒、背景、分离调色、局部调整、CMYK 色轮、灰点白平衡、**配方引擎**、HSL、**RAW 解码**
- **109 个 UI 控件**（117 个管线参数）+ 6 个配方 + 16 个 API 端点
- 7 个预设（自然 / 影楼 / 美颜 / 证件照 / 胶片 / 黑白）
- **7 个 AI 功能**：智能抠图、背景分离/换底、AI 追色、AI 挑图、AI 降噪（自训练）、
  **生成式填充（ComfyUI inpaint）**、**消除笔**
- **RAW 支持**：CR2/CR3/NEF/ARW/RAF/DNG/ORF/RW2，13 种去马赛克算法，16-bit
- FastAPI 后端 + 浏览器编辑器，参数实时预览

**没有做的事**：没有复制任何代码、没有解密任何加密资源、没有提取任何模型权重。
原软件 2GB 的加密资源包（`pixcook`）我明确没有尝试解密。

## 配方引擎（CraftFormula 的对应物）

`engine/formula.py`。配方比预设强在三点：**有序步骤**（同一控制可出现多次）、
**参数槽位**（`{{strength}}` 运行时绑定，一个配方适配多张图）、**可组合**
（配方引用配方）。四种步骤：`params` / `local` / `fill` / `formula`。

5 个内置配方：`skin_prep`、`clean_colour`、`cinematic`、`corner_vignette`（参数化）、
`portrait_full`（三步组合演示）。存 `formulas.json`，API 可增删查运行。

调试中抓到的核心缺陷：**数字槽位被 `str()` 化**。`{{mid_hue}}` 替换后变成
`"170"`（字符串），下游 `abs()` 直接崩。修法：整串就是一个槽引用时保留原类型，
只有嵌在文本里的引用才转字符串。

## 色轮与灰点（SelectColor / 白平衡取色器）

`engine/wheel.py`。色轮是 CMYK 六族（红黄绿青蓝洋红），选族 + 滑块；
灰点取色器从 patch 的通道比估计光源并全图校正。

验证用**逐像素追踪**而非窗口均值——旋转会把像素移出窗口，均值比较两个不同
总体。修正指标后：红族旋转 +39.5°（请求 40），其他族泄漏 ≤2.5°（羽化重叠）；
灰点把全局红蓝不平衡从 0.047 降到 **0.0015**（31 倍）。

## AI 功能

| 功能 | 做法 | 怎么验证的 |
|---|---|---|
| **智能抠图** | MODNet（24.7 MB）软 alpha + 亮度引导滤波贴边 | 脸内 alpha 1.000 vs 背景条 0.104 |
| **背景分离** | matte 合成：虚化 / 压暗 / 去色 / 纯色换底（证件照） | 各模式均通过，头发丝保留 |

| **AI 挑图** | 清晰度+曝光+对比+色彩，CLIP embedding 查重 | 清晰 0.819 > 模糊 0.421；重复帧正确归组 |

## RAW 支持

`engine/rawio.py`，基于 rawpy/LibRaw：

- **解码**：13 种去马赛克（LINEAR 493ms → AHD 439ms(half) → DCB/LMMSE/AMAZE 更慢更精）
- **白平衡**：机内 / 日光 / 手动四通道乘数
- **曝光归一化**：线性 RAW 打开是黑的（实测 median 0.0018），以 **p95 亮度**为锚点
  增益，配 filmic 软肩部防高光裁剪。曾试过用 median 锚点——对一张舞池照要求
  165 倍增益，14% 高光溢出；换成 p95 后问题消失
- **16-bit 输出**，**高光恢复**（`exp_shift`+`exp_preserve_highlights`），
  **原生降噪**（FBDD）
- **服务端**：上传按 RAW 分流（曾被存成 .jpg 再解码，报"cannot decode image"），
  预览用 half-size（449ms），**导出时重新全尺寸解码**（1225ms）保留全部传感器数据

### 打包踩到的三个坑（都已修）

**1. 模型路径在打包后失效**
原来各模块用 `__file__` 往上两级找项目根。打包后 `__file__` 指向
`_internal` 里，找到的是不存在的位置。统一改走 `engine/paths.py` 的
`models_dir()/data_dir()/web_dir()`，按 `sys.frozen` 分派。

**2. GPU 静默回退 CPU（最隐蔽的一个）**
PyInstaller 把 `torch/lib` 下的 cublas/cudnn 一并收进了包内，但 Windows
默认 DLL 搜索路径里没有那个目录。表现极具欺骗性：

- `torch.cuda.is_available()` → **True**
- `torch.cuda.get_device_name()` → 正确报出 RTX 3080
- 真正分配显存时找不到 `cublasLt64_12.dll`，torch 吞掉异常回退 CPU
- 结果：超清从 **9.2s 变 109s**，而诊断信息看起来一切正常

修法是 `engine/paths.py::register_cuda_dlls()` 用
`os.add_dll_directory()` 把 `torch/lib` 显式加进搜索路径，且必须
**早于任何 torch import** 调用（`tools/launch.py` 顶部 + `app.py` 导入区）。

为此新增了 `/api/diagnose`：它不只报 `is_available()`，而是真的在 GPU 上
跑一次矩阵乘并报耗时与显存，把"假阳性"变成可验证的事实。

**3. 挑图原来要拖 4GB 的 torch**
「挑图」只用到 CLIP 的**图像塔**，却在 `clip_available()` 里同时要求
`transformers` + `torch`。这等于为一个图像编码器把主程序撑大 4GB。

现在有第二条路：`engine/cliponnx.py` 用 onnxruntime 跑导出的
`clip_image_encoder.onnx`（335MB）。两条路输出契约一致（512 维、
L2 归一化），实测交叉验证：同一对图，transformers 余弦 0.5097、
ONNX 0.5023，差 0.007 —— 排序结果完全一致。

导出命令：`python tools/export_clip_onnx.py`

### 生成式三件套是可选组件

## 设计要点

**参数单调性。** 每个滑块必须单调，`tests/monotonic.py` 专门验证。

**背景保护是逐算子的。** `shadows` 最侵入暗背景（实测背景变化是主体的 5 倍，
权重压到 0.06），`contrast`/`highlights` 保持 0.51 维持调色连贯。
修复后背景亮度变化 **+0.080 → +0.008**。

**两类掩膜，用途不同。** 几何掩膜（region_mask）给祛痘——色度会把斑点本身
排除掉；色度掩膜（skin_mask）给磨皮——正确避开眼睛嘴唇头发背景。

**只在亮度通道做锐化。** 三通道各自 unsharp 产生品红/青镶边。

**HSV 提饱和度会压暗画面。** V=max(RGB)，提 S 会压其他通道——
`global_sat +50` 曾把亮度 0.377 拉到 0.273。加亮度补偿后只降 0.024。

**Lab 追色必须联合匹配。** 独立重映射 L 会破坏饱和度（实测 0.167→0.072，
占全部损失的 90%）；色度按亮度比例缩放后修复。

### 新补的三项公开模型能力

| 能力 | 模型 | 许可 | 为什么选它 |
|---|---|---|---|
| **AI 超清 4×** | Real-ESRGAN x4plus | BSD-3 | 之前完全没有超分；架构公开，自己实现省掉 basicsr 依赖 |
| **智能消除** | LaMa | Apache-2.0 | 局部、确定性、1~2 秒，不需要 prompt；替代"必须开着 ComfyUI"的 30 秒路径 |
| **语义分区** | selfie_multiclass | Apache-2.0 | 6 类语义，配饰单独成类 |

超分用 **tile 分块**不是优化而是必需：4× 模型在 24MP 上产生 384MP 中间结果，
float32 下每个激活就是 1.5GB，而这块 3080 只有 10GB。**并测了 tile 尺寸稳定性
（平均差 0.00118）**——接缝会表现为两次运行结果的差异。

**LaMa 的输出是 0–255 而不是 0–1**，这一点花了四轮探测才找到：把它当 [0,1] 裁剪，
所有 >1 的值全被压成白色，"填补"回来看起来是一片纯白（96.7%）。现在从输出自身
检测量程，0–255 / [0,1] / [-1,1] 三种导出都能正确归一化。
另外，LaMa 的契约是**洞里的像素已经清零**（官方管线先做 `image * (1 - mask)`），
喂进带内容的洞会让模型吐出平白区域。

### 布局不变量（这轮修的问题）

功能测试全绿但界面是坏的，所以单独加了一套布局断言：

* 移动端 **19 个分类挤在 390px 里**，"存在感"折成两行并和相邻标签重叠 →
  改成固定宽度 + 横向滚动（同时断言"任意两个 tab 不重叠、标签不溢出自身宽度"）
* 抽屉是浮层，画布仍在**整个高度**里居中，照片被推到抽屉后面、上方留大片死区 →
  抽屉打开时给画布让出 58vh；并且**人脸框要用新的位置重算**（原来它留在照片
  原来的位置上，飘在下方黑区里）
* 状态栏只在两个函数里被写入，任何不经过 render 的路径都会让"未载入图片"
  和一张明显已载入的照片同时出现 → 改成从状态派生（`updateMeta()`）
* 左栏 19 项溢出并裁掉最后几项 → 收紧行高，断言"内容不溢出"


### 局部调整曾把整个画面裁了一遍

`apply_local` 开头对整帧做了 `np.clip(img, 0, 1)`，末尾又裁一次。解码后的图像可以合法地
带上略超 1.0 的值（实测顶边 87 个像素为 `1.0000001`），于是**一个只作用于 7% 画面的蒙版
改动了其余 93% 的像素**，各差 1 ULP。同类问题在笔刷里也出现过一次。

现在只在实际写入的区域裁剪。空条目列表直接原样返回。测试的"掩膜外"也必须定义为
`m == 0` 而不是 `m <= 1e-6`——羽化尾部有大量 `0 < m ≤ 1e-6` 的像素，它们本来就在掩膜内。

### 配方里的字符串数字会半路炸掉

配方从三个地方进库：手写 JSON、编辑器 UI、HTTP 请求体。只有第一个是有类型的。网页表单
送来 `"170"`，字符串一路活到引擎层，在第 N 步执行到 `abs("170")` 或 `"20" / 100.0` 时
抛 TypeError——**此时前面的步骤已经应用了**。现在 `upsert` 在入口做递归规范化，字符串
无法越过这道边界。前导零（`"007"`）和含 `{{slot}}` 的模板串保持原样。

### 局部性测试抓到的缺陷（全部已修）

两者共用同一套采样，区别就在一个低频项：

```
clone(x) = P_src(x)
heal(x)  = P_src(x) - blur(P_src)(x) + blur(P_dst)(x)
```

图章**精确**复制——这正是它的用途（复制纹理、延展图案），也是它在光源不同的位置会露出
接缝的原因：粘贴的补丁带走了源的亮度。修复则保留源的**高频**（纹理、毛孔），取目标的
**低频**（色彩与光照），所以跨明暗边界时接缝小得多。

实测（跨明暗边界涂抹）：目标亮度 0.706，图章落点 0.049，修复落点 0.586——修复贴近环境
而图章明显错位；同时修复保留了源的高频（源 10.1 / 修复 11.6）。

### 自动白平衡必须在线性光下做

这一条踩了两轮才理清。**光源是线性光上的乘法增益**，一个 1.35× 的线性增益在 gamma
编码图上只表现为约 `1.35^(1/2.2) ≈ 1.15`。在编码空间里估计，得到的数字对那个空间是对的，
但作为线性校正去施加时**只能消掉约一半色偏**（实测 52%，修正后 93%）。

配套的三次度量修正同样值得记下：用全图 `|a*|+|b*|` 均值测"色偏"量的是**场景自身**的颜色
（这张是蓝霓虹夜景，固有色彩把强加的色偏完全淹没）；在 gamma 空间评估线性校正本身就不自洽；
而拿"均值灰世界"的理想逆去要求 `shades`（p=6 范数）是**范畴错误**——两者目标的中性不同。
分层测法才说清问题：`grey`（p=1）在灰世界帧上恢复到 **0.006**（近精确），`shades` 显著改善
但按其定义不会精确反演。

### 局部性测试抓到的缺陷（全部已修）

自然三次样条在控制点接近时会**过冲**——本该平直的一段被抬进裁切，而且控制点越多越糟。
实测同一组近点上自然样条过冲 **1.53**，而 PCHIP 为 **0**。所有暴露曲线的修图软件都因此用单调插值。

色阶则改成**闭式公式**而非查表：1024 项的表会把裁切边界抹开一格（实测 0.001 误差），
而公式既精确又更快。色阶的**裁切是有意的**——低于黑场的像素全压到黑场，所以可逆性只在
输入范围内成立，测试也按这个断言（范围内往返 0.00000）。

### 撤销栈的两个设计选择

- **快照而非操作日志**：五个破坏性操作都不可从参数反演（填充是合成的、色轮作用在已调色
  的像素上），而且填充结果依赖随机种子，重放根本复现不出同一个结果。
- **8 位 PNG 存储**：容器无损但量化到 8 位，恢复误差 ≤ 0.5/255。这是有意的——8 位就是显示
  精度，导出 JPEG 也是这个上限，存更高精度要多花 12 倍内存而看不出差别。关键是**反复撤销
  重做不累积误差**：每个状态只编码一次，而不是重新推导。

### 局部性测试抓到的缺陷（全部已修）

局部性断言是这套测试里性价比最高的一项：它假设**掩膜外的像素必须逐位不变**，
把「效果有点偏」这种模糊观感变成带坐标的硬失败。

| 操作 | 泄漏量（修复前） | 根因 | 修复 |
|---|---|---|---|
| `even_skin_tone` | **0.4674** | 收了 `mask` 却只用于祛红，**色度平滑是全图**的——背景强色彩被静默去饱和 | 色度平滑也乘 mask |
| `eye_bag_reduction` | 0.0080 | 重建整帧 Lab，而 **Lab 往返不是无损**（实测 0.0039） | 改为按 mask 在 RGB 空间混合 |
| `eye_highlight` | 0.0080 | 同上 | 同上 |
| `teeth_whiten` | 0.0061 | `srgb_to_linear` → `linear_to_srgb` 全图往返同样有损 | 同上 |
| `retouch_skin`（集成） | 0.1918 | 上述几项累积 | 随各项修复 |

修复后全部 ≤ **0.0002**（远低于 1/255 容差）。两个副产物：**背景色彩不再被压灰**
（画质提升），以及**性能更好**（不再做整帧色彩空间往返）。

### 液化有更强的契约：逐位精确

液化用的是 `cv2.remap` 重采样，直觉上"整帧都会被重采样改变"——**实测不是**。
Lanczos4 在整数偏移处是精确恒等，所以：

| 操作 | 位移为零的像素 | 该区域 max\|diff\| | 位移非零处 |
|---|---|---|---|
| 零位移 warp（含边界） | 100% | **0.0000000** | — |
| `slimFace(60)+jaw(40)` | 82.2% | **0.0000000** | 0.8495 |
| `enlargeEye(60)` | 82.2% | **0.0000000** | 0.8324 |
| `reshape_body(瘦腿)` | 84.5% | **0.0000000** | 0.2336 |

这比 1/255 容差强得多——是**逐位相等**。`reshape_face`/`reshape_body` 因此增加了
`return_field=True` 选项，让测试断言**同一份位移场**，而不是在测试里重新推导几何
（那样会随实现漂移）。

测试自身也修了两处度量错误：目标区域曾用几何脸框，而色度皮肤掩膜合法地延伸到脖子，
于是报出"假泄漏"；背景保护和换背景需要各自的断言形式——前者比较"有保护 vs 无保护"
（实测背景变化下降 2.9x、主体保留 98%），后者是反极性（主体不变而背景必须变）。


## 已知限制

- **2d106det 对浓妆/假发/非正面失准**（与 insightface 官方管线交叉验证过，
  是模型边界而非实现 bug）
- **姿态估计只对可见身体有效**，头肩像退回画面几何
- **RAW 相机档案未接**：色彩矩阵用 LibRaw 内置的，没有逐机型标定数据
- **生成式三件套是可选组件**：需要外挂 ComfyUI + 13GB 模型，
  见 `GENERATIVE.md`（`tools/install_generative.py` 一键安装）
- **降噪模型只在合成噪声上训练**：真实高 ISO 的噪声结构更复杂（行噪声、
  量化耦合），下一步应引入真实噪声对（暗场帧）
- **无代码签名时 SmartScreen 会警告**：见下面「发布」章节

## 发布（发版流程）

1. 改版本号：`server/app.py` 里的 `APP_VERSION`（唯一来源；
   exe 属性、`/api/version`、关于面板都跟着它走）。
2. 打包：`build_app.bat`（PyInstaller + assemble_dist）。
   产物带 `build-stamp.txt`（构建日期），随包附 `install_generative.py`
   与生成式安装指南。
3. 代码签名（发行给外部用户时强烈建议，否则 SmartScreen 弹"未知发布者"）：

   ```powershell
   $env:RETOUCHLAB_CERT_PFX = "D:\certs\mycode.pfx"   # 代码签名证书
   $env:RETOUCHLAB_CERT_PASS = "..."                  # 证书密码
   python tools\assemble_dist.py                      # 自动调 signtool
   ```

   证书怎么买（2026 年行情，本项目已验证签名链路端到端可用——
   自签证书实测：signtool 签名 + 时间戳 + 链验证全部通过，只差
   一个受信的 CA 根）：
   - **Certum 开源开发者证书**（约 €25-70/年）：**本项目最对口**——
     专门发给公开源码项目，费用低，签出的就是正规 OV 代码签名。
     https://certum.eu 的 "Open Source Code Signing"。
   - **SignPath.io 开源免费计划**：公开仓库可申请免费签名服务，
     需要申请审核（https://signpath.io）。
   - **Azure Trusted Signing**（$9.99/月，个人开发者可申请）：
     微软自家服务，SmartScreen 信誉积累快。
   - **EV 代码签名证书**（硬件 USB Token，几千元/年）：SmartScreen
     立即信任，预算充足的最省心选择。
   - **自签证书**：只适合验证链路（本仓库就是这么测的），对外部
     用户毫无信任价值。
   - 没有证书时 assemble_dist 会跳过签名并提示，本地打包不受影响。
4. 更新检查：`/api/version` 返回 `update_url`（GitHub Releases 的
   latest 接口），前端关于面板据此提示新版本。**仓库需要公开**（或把
   `update_url` 换成你的分发地址）检查才会生效；仓库不可达时静默降级。
5. 崩溃上报：发行版的排障入口是「关于 → 复制诊断报告」，把版本、
   GPU 实测（`/api/diagnose`）、最近 5 条异常（`/api/errors`，来自
   `out/error.log`）一次复制给维护者。
